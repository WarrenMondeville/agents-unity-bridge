# Agents Unity Bridge 原理与命令清单

> 本文整理自对 `agents-unity-bridge` 源码（Unity 包 `package/` 与 Python CLI `skill/`）的通读，
> 面向想快速理解这套代码「为什么这样设计、如何工作、有哪些命令」的读者。

---

## 一、一句话概括

`agents-unity-bridge` 是一个**基于文件的跨进程 RPC 桥**：让 DeepSeek Harness（外部进程，通过 Python CLI）能够遥控一个正在运行的 Unity Editor 去执行「跑测试 / 编译 / 构建 / 控制 PlayMode / 查日志 / 查状态 / 资源依赖分析」等操作。

它不靠网络、不靠端口，只靠一个约定目录里的两个 JSON 文件做「投信—回信」。

---

## 二、两大组件

| 组件 | 位置 | 语言 | 角色 |
|---|---|---|---|
| Unity 包 | `package/Editor/` | C# | **服务端**：在 Unity 里轮询命令、执行、写回结果 |
| Skill CLI | `skill/src/agents_unity_bridge/cli.py` | Python | **客户端**：写命令、等结果、格式化打印 |

两端通过一个共享目录通信（**每个 Unity 项目各有一个**，互不干扰）：

```
<Unity项目根目录>/.agents-unity-bridge/
├── command.json            # 客户端 → Unity 的命令（一条）
└── response-<uuid>.json    # Unity → 客户端的结果（每个命令一个）
```

---

## 三、核心：文件协议（一次完整请求的生命周期）

```
Python CLI                          Unity Editor (AgentsBridge.cs)
    │                                        │
    │ 1. 生成 UUID，原子写入 command.json     │
    │    {id, action, params}               │
    │────────────────────────────────────────>
    │                                        │ 2. EditorApplication.update 每帧
    │                                        │    轮询 command.json 是否存在
    │                                        │ 3. 读到后【立刻删除】command.json
    │                                        │    （防重复执行）
    │                                        │ 4. 查字典找到对应命令，执行
    │                                        │
    │ 5. 指数退避轮询 response-<id>.json      │ 6. 原子写入 response-<id>.json
    │<────────────────────────────────────────
    │ 7. 解析、格式化打印、删除 response 文件 │
```

这条链路最关键的**对称设计**是：**写命令 = 原子写；写响应 = 原子写**。所以任何时刻磁盘上都不会出现「写了一半的 JSON」被对方读到。

## 四、关键机制（「原理」的精华）

### 1. 原子写（Atomic Write）

两端都先写 `.tmp` 临时文件，再 `replace` / `File.Move` 覆盖目标文件：

- Python：`cli.py` 的 `write_command()`
- C#：`AgentsBridge.cs` 的 `WriteResponse()`

这样避免「对方读到半截文件 → JSON 解析失败」。

### 2. UUID 关联 + 防路径穿越

每个命令生成一个 UUID 作为「会话 ID」，响应文件名用 `response-{id}.json` 关联。

- 安全点：响应 ID 必须匹配正则 `^[a-fA-F0-9\-]+$`、UUID 格式校验，**防止把 id 写成 `../../evil` 造成路径穿越**。
- Python 还拒绝 `.agents-unity-bridge` 是符号链接。

### 3. 轮询 + 指数退避

Python 等响应时不是死等，而是：

- 起始睡眠 `0.1s` → 每次 ×1.5 → 封顶 `1.0s`
- 读到 `status: "running"` 就继续等（Unity 会多次写进度），读到终态才返回

### 4. 「忙/编译中」保护（Unity 侧状态机）

`AgentsBridge.PollForCommands()` 有三级判断：

1. **正在处理上一条命令** → 拒绝新命令，回 `error` 让客户端不挂起。
2. **Unity 正在编译/更新资源**（`isCompiling || isUpdating`）→ 只放行只读命令 `get-status`、`get-console-logs`、6 个资源依赖分析命令（`get-dependencies` / `find-references` / `find-unused-assets` / `trace-path` / `search-assets` / `get-asset-info`）以及 `dump-asset`，其它一律拒绝（白名单 `SafeDuringCompileCommands`）。**核心原则：绝不在编译时打断 Unity；这些查询本身是只读的，所以编译期间也能用。**
3. 空闲 → 正常 `ProcessCommand()`。

### 5. 超时自恢复

- Unity 侧：单命令卡住超过 5 分钟自动 `ResetProcessingState()` 复位。
- Python 侧：命令超时抛 `CommandTimeoutError`（退出码 2）、Unity 没运行抛 `UnityNotRunningError`（退出码 1）、成功退出码 0。

### 6. 结果的状态机

响应 `status` 有 4 态：

| status | 含义 |
|---|---|
| `running` | 进度中间态（如测试跑到第几个） |
| `success` | 成功 |
| `failure` | 执行完但有失败（如测试有失败项） |
| `error` | 异常 / 参数错 / 未知命令 |

## 五、Unity 侧：命令模式（Command Pattern）

这是包内部的结构化方式。

`ICommand` 接口只定义一件事（`package/Editor/Commands/ICommand.cs`）：

```csharp
public interface ICommand {
    void Execute(
        CommandRequest request,
        Action<CommandResponse> onProgress,
        Action<CommandResponse> onComplete
    );
}
```

`AgentsBridge` 静态构造函数里建了一张 **action → 命令对象** 的字典（`AgentsBridge.cs`）：

```csharp
Commands = new Dictionary<string, ICommand> {
    { "run-tests", new RunTestsCommand() },
    { "compile", new CompileCommand() },
    { "refresh", new RefreshCommand() },
    { "get-status", new GetStatusCommand() },
    { "get-console-logs", new GetConsoleLogsCommand() },
    { "play", new PlayCommand(playMode) },
    { "pause", new PauseCommand(playMode) },
    { "step", new StepCommand(playMode) },
    { "build", new BuildCommand() },
    { "get-dependencies", new GetDependenciesCommand() },
    { "find-references", new FindReferencesCommand() },
    { "find-unused-assets", new FindUnusedAssetsCommand() },
    { "trace-path", new TracePathCommand() },
    { "search-assets", new SearchAssetsCommand() },
    { "get-asset-info", new GetAssetInfoCommand() },
    { "manage-prefabs", new ManagePrefabsCommand() },
    { "dump-asset", new DumpAssetCommand() }
};
```

执行时通过 `Commands.TryGetValue(request.action)` 分发，命令通过**回调**而非返回值上报结果——这才能支持异步长任务。

### 各命令的实现要点（体现不同模式）

- **`CompileCommand`（异步事件）**：`RequestScriptCompilation()` 后**不阻塞**，挂到 `CompilationPipeline.compilationFinished` 事件上，等 Unity 编译完回调再回 `success/failure`。
- **`RunTestsCommand`（回调 + 进度）**：实现 Unity Test Runner 的 `ICallbacks`，在 `TestStarted/TestFinished/RunFinished` 里累计 `passed/failed/skipped`，不断通过 `onProgress` 回写 `running` 进度。
- **`BuildCommand`（双模式）**：
  - `direct` 模式：直接 `BuildPipeline.BuildPlayer()`；
  - `method` 模式：用**反射**定位 `Namespace.Class.Method` 静态方法并 `Invoke`，支持设置环境变量、结束后恢复——便于调用项目自定义构建入口。
- **`GetConsoleLogsCommand`（反射）**：通过反射访问 Unity 内部 `UnityEditor.LogEntries`（非公开 API），按 `mode` 位掩码区分 Log/Warning/Error。
- **`PlayCommand/PauseCommand/StepCommand`**：通过 `IEditorPlayMode` 接口隔离 Unity 的 `EditorApplication` 依赖（便于单测替换），本质是设置 `isPlaying / isPaused / Step()`。
- **资源依赖分析 6 命令**（`GetDependenciesCommand` / `FindReferencesCommand` / `FindUnusedAssetsCommand` / `TracePathCommand` / `SearchAssetsCommand` / `GetAssetInfoCommand`）：全部**只读**，直接调用 Unity 原生 `AssetDatabase`（`GetDependencies` / `FindAssets` / `AssetPathToGUID` / `GUIDToAssetPath` 等），共享 `AssetAnalysisUtil` 做「路径/GUID 解析 + bool/int 字符串解析」。
  - `get-dependencies` → `AssetDatabase.GetDependencies(path, recursive)`（正向依赖，可选递归闭包）。
  - `find-references` → 遍历 `GetAllAssetPaths` 逐个 `GetDependencies(..., false)` 反查（Unity 无反向索引，O(N) 扫描）。
  - `find-unused-assets` → 以「Build Settings 启用的场景 + `Resources/` 目录」为根做可达闭包，不可达者即候选（排除 `.cs/.asmdef/.asmref`）。
  - `trace-path` → 正向依赖图上 BFS 求最短路径，`maxDepth` 限深。
  - `search-assets` → `AssetDatabase.FindAssets("query t:type")` + `GUIDToAssetPath`。
  - `get-asset-info` → 单资源的 GUID / 类型 / 文件大小 / 直接与递归依赖数。
- **`ManagePrefabsCommand`（manage-prefabs）**：预制体管理，直接调用 Unity `PrefabUtility`。子动作通过 `params.prefabAction` 分派：
  - `get-info` → 元信息（GUID / PrefabAssetType / 根组件类型 / 子对象数 / Variant 父级）。
  - `get-hierarchy` → 用 `PrefabUtility.LoadPrefabContents` 加载后遍历层级（名称/路径/组件/嵌套预制体信息），用后 `UnloadPrefabContents` 释放。
  - `create` → 在活动场景或预制体舞台里按名找 GameObject，`PrefabUtility.SaveAsPrefabAssetAndConnect` 存成 `.prefab`（支持 `allowOverwrite` 覆盖、`unlinkIfInstance` 先解绑实例）。
  - 其中 `get-info` / `get-hierarchy` 只读；`create` 会写资产库，故**未**加入编译期白名单。
- **`DumpAssetCommand`（dump-asset）**：导出资产的 Inspector 可见序列化字段值（对应参考项目 `unity-prefab-parser-mcp` 的 `parse_unity_file` 核心能力）。按扩展名分派：
  - `.prefab` → `PrefabUtility.LoadPrefabContents` 遍历 GameObject 树；`.asset` → `AssetDatabase.LoadMainAssetAtPath`；`.unity` → 当前打开场景的根对象。
  - 用 `SerializedObject` + `SerializedProperty.NextVisible` 遍历，天然只输出 Inspector 可见字段（过滤内部字段），`m_LocalPosition` 重命名为 `localPosition`。
  - MonoBehaviour / ScriptableObject 用 `m_Script` GUID 解析脚本名作为组件显示名。
  - 分类型提取值：Vector3 → `(x, y, z)`、枚举 → 枚举名、ObjectReference → 资产路径、数组 → `[N items]`。
  - 只读，已加入编译期白名单。
  - **与参考项目 `unity-prefab-parser-mcp` 的关键区别**：后者在 Unity 之外解析文本序列化 YAML（需 Force Text）；bridge 用 `SerializedObject` 拿实时数据，无需文本序列化、无需 `.meta` 缓存。
  - **与参考项目 `uasset-reference-memory-mcp` 的关键区别**：后者在 Unity 之外解析 `.meta` + YAML 建 SQLite 图；bridge 跑在 Unity 内部，`AssetDatabase` 本身就是「现成的实时索引」，所以**无需提前建库、无需索引步骤**，答案永远实时。

## 六、Python 侧：CLI

`cli.py` 是「**确定性执行器**」——设计初衷就是所有边界情况在脚本里统一处理一次，而不是让 AI 每次在上下文里临时实现。

它主要做四件事：

1. **组装并原子写命令**：`write_command()`（生成 UUID、mkdir、写 tmp、replace）。
2. **轮询等待响应**：`wait_for_response()`（指数退避、`running` 续等、JSON 解析重试）。
3. **格式化输出**：`format_response()` 按 action 分派到 `format_test_results / format_compile_results / format_build_results ...`，把原始 JSON 变成带 `✓ ✗ ○` 的人类可读文本。
4. **收尾清理**：删旧响应文件、删过期 `command.json`、删本次响应文件。

另有 `install-skill / uninstall-skill / update` 负责把 SKILL.md 装到 `~/.dsh/skills/unity-bridge`（Windows 下符号链接失败则退化为目录拷贝）。

---

## 七、为什么选「文件协议」而不是网络

1. **零网络配置**：不用开端口、不用配防火墙、无端口冲突。
2. **多项目隔离**：每个 Unity 工程自带 `.agents-unity-bridge/`，可同时遥控多个工程。
3. **天然可调试**：直接 `cat` 那两个 JSON 就知道卡在哪。
4. **天然解耦**：Python 和 Unity 是两个独立进程，只约定目录和 JSON 格式即可。
5. **确定性**：所有 UUID、轮询、超时、文件锁、异常处理集中在一个测试过的脚本里，行为每次一致。

## 十、一句话总结原理

> 客户端把「动作 + 参数 + UUID」原子写入 `command.json`；Unity 里一个 `[InitializeOnLoad]` 的静态类在每帧 `EditorApplication.update` 里轮询到这个文件，删除它防止重放，按 action 分发给对应的 `ICommand` 执行，再原子写回 `response-{uuid}.json`；客户端用指数退避轮询到终态后格式化输出并清理。整个过程靠「原子写 + UUID 关联 + 状态机防忙 + 超时自恢复」保证了可靠性和安全性。
